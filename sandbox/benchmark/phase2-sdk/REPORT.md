# 阶段2：公开SDK压测与应用场景总览

本阶段包含与协议客户端匹配的公开SDK调用，以及官方Code Interpreter性能序列。主矩阵39个有效run，共1,016,866个测量请求，19次失败均在C=N=64短命令场景；全部归属清理通过。

## 结果入口

- [主矩阵](MAIN-RESULTS.md)：SDK吞吐/长尾/失败、首条计时调用与后续调用分组。
- [官方SDK应用序列](APPLICATION-RESULTS.md)：60个新实例、四阶段240个操作、配对首次/第二次代码执行。
- [多发生器](MULTIGENERATOR-RESULTS.md)：global C64/N64固定，4进程对照、边界外失败保留。
- [生命周期对照](../phase1-service/LIFECYCLE-RESULTS.md)：SDK与协议控制路径的pause/resume及状态校验。
- [补充条件](SUPPLEMENTAL-RESULTS.md)：文件编码、记录处理、逐slot预热等独立场景，不混为主矩阵重复。

## 可据此作出的判断

SDK短命令吞吐在C=N=32约2025次/秒，C=N=64约1957次/秒；增加并发并没有继续提高主矩阵吞吐，长尾和首次请求错误反而需要关注。

19个错误中18个位于worker第一条计时请求：18/192=9.375%，不同于整体19/171,510=0.01108%。这是请求位置关联，不能证明某个网络或SDK函数是唯一根因。逐sandbox执行过命令后，在C64测量仍出现连接重置；不能把“slot使用过”说成所有传输连接已预建立。

官方SDK序列从创建开始到首次代码结果的配对P50约2.155秒，而创建本身约270毫秒；第一次解释器调用约1027毫秒，第二次约68毫秒。首次使用与热调用应分开，SDK总时间不能直接减服务端均值来认定包装开销。

使用的Code Interpreter模板保留官方server与Python/JS kernel，省略完整云模板的其他语言和大量包。完整配置、依赖、模板身份、脚本和复现步骤见[README](README.md)。本轮没有调用LLM或运行RL。
