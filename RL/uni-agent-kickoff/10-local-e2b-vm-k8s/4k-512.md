## 目标与边界

客户端入口保持 `http://10.145.64.67:8088`，`E2B_API_URL` 与 `E2B_SANDBOX_URL` 都使用它。原 API key 继续保存在宿主机私有目录，报告不包含密钥。

目标配置：

| 项目 | 值 |
|---|---|
| Sandbox guest RAM | 普通 4 KiB 页 |
| 显式 HugeTLB 池 | 0 |
| 团队运行配额 | 512 |
| 节点运行配额 | 512 |
| 内核 NBD 设备 | 1024 |
| NBD 预热缓存 | 32，保持上游设置 |
| 同时启动/恢复的节点准入 | 3，保持上游设置 |
| IPv4 / IPv6 邻居表 GC 阈值 | 4096 / 8192 / 16384 |
| QEMU 文件描述符限制 | 1048576 |
| Nginx worker 文件描述符限制 | 65536 |
| 外层 VM | 192 vCPU、分配 1511 GiB，Linux 实际可见约 1486.84 GiB |
| VM 磁盘 | 1 TiB qcow2，位于 `/data2` |

512 是允许同时运行的数量上限，不是 512 份满配内存的预留。512 × 4 GiB = 2 TiB，超过现有 VM 物理内存。普通页让内存按实际访问分配；在所有任务同时使用大量内存时仍会耗尽资源。验收只验证轻量命令、隔离和生命周期，不写满各实例的 4 GiB。

## 为什么需要自定义 runtime

固定上游源码为 `e7b22501988c826563bf1b3cf0d22a1183e7affe`。官方 Embed 默认在模板构建与部分创建流程中根据 Firecracker 版本启用 HugeTLB；节点上限的默认值是 200，当前离线部署没有现成环境变量覆盖入口。

本地补丁新增：

- `E2B_SANDBOX_HUGE_PAGES=false`：API 和同时承担 orchestrator/template-manager 两种角色的进程都设置。三处调用共同选择普通页，保留 `HasHugePages()` 原本的能力判断。
- `E2B_MAX_SANDBOXES_PER_NODE=512`：为节点功能开关提供本地默认值；若另行配置 LaunchDarkly，远端值仍有优先权。
- `host-setup.sh`：普通页模式允许 `HUGEPAGES=0`，同时同步历史 cloud-init 留下的 `90-e2b-capacity.conf`，防止重启重新预留。

这两个 `E2B_*` 环境变量来自本地补丁，不能直接用于未修改的官方二进制。补丁未关闭 KVM、UFFD、MEMFD 或沙箱隔离。

API、orchestrator 和数据库迁移器编译自同一份源码，使用 Go 1.26.8。API/迁移器为静态二进制，orchestrator 使用 CGO，构建系统与 VM 均为 Ubuntu 24.04 / glibc 2.39。Go 工具链、依赖缓存和二进制留在 `/data2` 的运行工作区，不放入文档仓库。

旧发布制品标识含 `59497eb9134`，该 revision 无法在公开 runtime 仓库解析，因此没有声称本次编译复现了旧发布二进制。新 API 需要固定源码自带的数据库版本 `20260915204740`。维护前已做完整 PostgreSQL 备份；升级应用三条待执行的官方迁移，其中待删除的旧头像字段原本不存在。

## 部署结构

沿用 K3s StatefulSet 和官方镜像，用只读 hostPath 挂载自定义文件：

```text
VM /opt/e2b-local/custom-runtime/
  api
  orchestrator
  migrator
  host-setup.sh
  migrations/          # 固定源码的全部 SQL 迁移
```

API 容器执行挂载的 `api`；数据库迁移 init container 在该目录运行 `migrator`。orchestrator 保留官方 launcher 的生命周期清理逻辑，使用 `OL_COMMAND` 指向自定义二进制。

官方 `fetch-artifacts` 继续维护 `/var/lib/e2b/bin/orchestrator` 等原制品，不覆盖自定义目录。Pod template annotation 记录 API/orchestrator SHA-256；替换二进制后应同步 annotation 并滚动重启。不得直接覆盖正在运行的可执行文件，应先暂存，再原子替换或在服务停止时安装。

## 在相同布局下构建

运行工作区默认 `/data2/yuhanya/e2b-local-20260916`。可以通过 `E2B_LOCAL_ROOT` 修改构建根目录；部署 VM 内的路径仍需与 Kubernetes hostPath 一致。

1. 在 `build/runtime-4k-20260920` 获取固定源码，应用 `patches/runtime-4k-512.patch`。补丁包含新增文件，不能只复制已有文件的 diff。
2. 将经官方 SHA-256 校验的 Go 1.26.8 解压到 `toolchain/go1.26.8/`，使 `toolchain/go1.26.8/go/bin/go` 可执行；构建机需 GCC 和兼容 VM 的 glibc。
3. 分别执行 `bash code/build_runtime_4k.sh api`、`orchestrator`、`migrator`。构建脚本输出各二进制 SHA-256。
4. 将三个二进制、源码 `packages/db/migrations/`、打过补丁的 `embed/compose/scripts/host-setup.sh` 安装到 VM 的上述目录。
5. 使用本实验的 `capacity.yaml`、`runtime-local.yaml` 以及原网关和密钥引用配置。不要重新生成已有 API key。

宿主机 QEMU 的 systemd 单元还需 `LimitNOFILE=1048576`。可安装本实验的 `e2b-sandbox-vm.service.d/20-e2b-capacity.conf` drop-in 并 `daemon-reload`；对已经运行的 QEMU，核对 MainPID 后用 `prlimit` 同步更新当前进程。网关配置包含 `worker_rlimit_nofile 65536`。

VM 内将 `configs/91-e2b-network-capacity.conf` 安装到 `/etc/sysctl.d/` 并用 `sysctl -p` 应用。更新后的 `install_guest.sh` 已包含这个步骤。该文件为 IPv4、IPv6 的邻居表配置 4096/8192/16384 三档 GC 阈值。

## 从旧大页部署迁移

需要维护窗口。核心 Pod 重启会中断运行中的 sandbox；本次维护前查到运行实例为 0。

1. 备份 PostgreSQL、实际 StatefulSet、配置、模板当前 tag 指向的 build UUID。备份目录权限 0700，不上传含凭据的数据库 dump。
2. 先部署普通页 API/orchestrator，但暂保留旧大页池，便于迁移和回滚。现有 HugeTLB 快照不会因配置改变而自动变为普通页。
3. 在目标团队的 `project_limits` 中将运行配额设置为 512，保留其他有效限制，不改共享 tier。Redis auth cache 的 TTL 是 5 分钟；服务重启本身不会清空该缓存。
4. 停止核心 Pod，并确认 `/sys/block/nbd*/pid` 没有活动设备后，将 NBD 模块重新加载为 `nbds_max=1024`。配置持久化到 `/etc/modprobe.d/e2b-nbd.conf`。
5. 首先迁移 `base`，独立验证普通页和暂停恢复。其余模板由 `migrate_templates_4k.py` 处理：以旧名称及旧 build UUID 固定来源，复用磁盘文件，显式保留 CPU、内存、tag、start/ready 命令，冷启动生成新快照。
6. 原命令为 null 时向 API 传空字符串，不能发送 JSON null。注册和启动不是幂等操作，脚本在请求前保存状态，响应不明时不盲目重复 POST。
7. 全部当前 tag 迁移成功后，设置 `HUGEPAGES=0`，显式移除 K8s requests/limits 中的 `hugepages-2Mi`。基础 manifest 自带 `4Gi`，仅删除覆盖值会恢复这个默认值，必须用 `null` 或 JSON patch 删除键。
8. 完整重建核心 Pod，让 PostgreSQL 也先退出；原 PostgreSQL 的 `huge_pages=try` 会占用旧池。最终配置为 `huge_pages=off`。两份 sysctl 配置都归零，再更新 kubelet 的节点容量信息。
9. 再次检查重启后的页池、模板、API/key 和实际 sandbox 行为。

`configs/team-quota-512.sql` 中的团队 UUID 是本机实例的值。其他部署必须先确认 API key 所属团队并替换 UUID；脚本在目标不存在时会中止。

迁移脚本的 state 是断点记录，不能在失败后删除并直接重跑。`--dry-run` 不发请求；`--limit 1` 用于首个模板验收；完成项会跳过。同一个模板有未决构建时，不继续注册其他迁移。

历史 build UUID 的旧快照作为回滚材料保留，并未转换。正常名称/tag 改指向新的普通页构建。显式请求旧 UUID 仍可能依赖大页，不能把“保留旧构建”理解为“旧构建已完成页类型转换”。

## 验收方法

不能只检查配置或 memfile 的存储块大小。去重后的存储块可以是 4 KiB，但运行虚拟机仍使用 2 MiB 页。

本实验使用 `verify_guest_4k.py`，在外层 VM 内定位指定 sandbox 的 Firecracker，组合检查：

- `/machine-config` 的 `huge_pages` 为 `None`。
- `/memory/mappings` 中所有 guest 映射的 `page_size` 为 4096。
- 对应 `/proc/PID/smaps` 的 `KernelPageSize`、`MMUPageSize` 为 4 kB，HugeTLB/THP 计数为 0，没有 `ht` 标记。
- 暂停、恢复后重复检查，并验证文件标记保留。

最终再运行 SDK 命令、文件、退出码、HTTP 端口和清理检查。容量脚本使用 `base-4k-4g`（2 vCPU / 4096 MiB），创建并发为 2，达到 512 时验证全部实例存活及文件隔离，并检查第 513 个请求的配额错误。

`test_4k_capacity.py` 在每 64 个实例处读取 VM 可用内存，低于 64 GiB 停止并清理；异常时通过本次唯一 `run_id + purpose` 找回实例。恢复清理使用 `--cleanup-only --output 原报告路径`。该脚本不会删除其他任务的 sandbox。

前三次测试分别创建到 348、346、350 个实例后失败，表现为内部 RPC 超时、`503: no compatible node`、工具读取超时或创建 500；每次均清理了全部本次实例。记录的可用内存仍约 1.4 TiB，没有发现名义内存或 CPU 总量的调度拒绝，也没有发现 gRPC 消息超限。

第三次失败后，内核日志确认从第一次故障前就存在 `neighbour: arp_cache: neighbor table overflow!`。旧邻居表阈值是 128/512/1024；多个 microVM/网络 namespace 消耗同一节点的邻居表预算，数百实例触发了这个网络容量限制。此后将阈值提高到 4096/8192/16384，并在第四轮记录 `/proc/net/stat/arp_cache` 的 entries 峰值和 table_fulls 增量。不能把原先约 350 的卡点归因于物理 RAM。

排查期间也发现 QEMU 和 Nginx 的低文件描述符上限并作了扩容，但第三轮在扩容后仍失败，因此不把文件描述符调整单独认定为解决了原故障。

验收脚本随后增加对明确临时 503 的有界重试，最多额外 8 次，间隔为 1/2/4/8/8/8/8/8 秒，并保留全部失败记录。达到 512 后保持至少 60 秒、每 10 秒检查存活和内存，再执行全部实例的工具检查。429 配额错误及第 513 个探针不重试；服务端健康过滤和资源保护没有被关闭。两轮结果均保留在运行工作区。
