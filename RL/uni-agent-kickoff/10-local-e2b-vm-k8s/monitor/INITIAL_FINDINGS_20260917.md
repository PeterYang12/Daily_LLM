## 初步结论

1. **没有 CPU 总量不足的证据。** 在可见业务请求窗口内，VM CPU 平均 1.418%，约等于 192 vCPU 中 2.72 个核；P95 为 2.957%，最大 5.5%。活动 sandbox 的分钟采样平均 14.1 个、峰值 16 个。存在短暂单核热点，但没有持续耗尽整机 CPU。
2. **热模板下的创建速度较快。** 捕获的 3,338 次 API 创建请求均返回 201，API handler 延迟 P50=58.9 ms、P95=83.6 ms、P99=103.4 ms，最大约 312 ms。删除 P95=7.35 ms。它们是服务端计时，不包含远端完整 SDK 开销，也不能代表新镜像的冷下载/构建速度。
3. **未看到持续网络吞吐饱和。** 业务请求窗口内 VM 接收平均 0.911 MiB/s、发送平均 0.182 MiB/s；入口连接 TCP RTT P50=5.48 ms、P95=10.69 ms。VM 主网络命名空间记录的重传段数约占 OutSegs 的 0.013%。这些数据不支持“持续把带宽打满”的判断，但频繁串行 RPC 的延迟仍值得检查；TCP RTT 不等于单次业务请求延迟。
4. **更值得定位的是长命令和 Agent 等待。** 网关记录约 28.9 万次 `process.Process/Start`，P50=7 ms、P95=215 ms、P99≈2.01 s；其中 16 次超过 30 秒，6 次超过 60 秒，最长约 300 秒。该接口耗时包含命令运行、等待与输出传输，不能直接当作网络耗时。下一步优先对齐远端 Uni-Agent 的具体 tool call、测试执行和 LLM 等待，而不是直接增加服务端 CPU。
5. **告警与服务失败需要区分。** 健康历史没有记录到失败检查，告警主要由宿主机根分区空间触发：16:27 UTC 左右曾记录 `/` 可用空间为零。E2B 所在 `/data2` 与 VM 内根文件系统没有达到该阈值，VM 最低仍约有 215 GiB 可用。这是独立的运维风险，不能据此判定它造成了训练吞吐瓶颈。
