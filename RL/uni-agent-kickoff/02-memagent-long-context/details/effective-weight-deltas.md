# HF checkpoint 在 BF16 下的可见权重变化

只读审计脚本：`scripts/cpu-effective-weight-deltas.py`。完整逐 tensor 数值、文件路径、dtype 和统计：`results/effective-weight-deltas.json`。CPU Docker 内执行，GPU 不可见；未实例化模型、未生成回答、未修改 checkpoint 或 optimizer。

这组抽样表明：非零梯度实验既改变了 FP32 保存值，也改变了一部分统一 BF16 后的值。但两者的变化比例差别很大，不能用 master 参数的变化比例直接描述 rollout 可见变化，更不能据此推断任务能力提升。

## 抽样和计算口径

每个 checkpoint 读取 9 个相同角色的张量：第 0、中间、最后一层的 `q_proj.weight`、`o_proj.weight`、`input_layernorm.weight`。层号从 base config 动态确定：0.6B 为 0/14/27，4B 为 0/18/35。旧 RL analyzer 对两种模型均取 0/14/27；此处的 4B 抽样因此覆盖真正的中间层和末层，数值可能略有不同。

base 的实际 tensor dtype 均为 BF16，HF checkpoint 均为 FP32。stored 比较直接读取两边保存的数值；BF16 比较先分别 cast 两边。两种比较均用 FP64 计算差值统计，以精确容纳原 BF16/FP32 数值，changed 定义为严格不相等，没有 epsilon。比例按所读元素数加权，而不是九个 tensor 比例的平均。

所有检查均为 finite。零梯度 pilot `smoke` 在两种精度下都完全不变，作为负对照保留。

MemAgent 32 步末 checkpoint 中，62,894,028 个保存值发生变化，统一 BF16 后还有 1,057,746 个变化；约 98.3182% 的保存值变化被本次 BF16 舍入抹除。它并非完全没有可表示的权重变化，同时也不能从“约 99.96% 的 FP32 元素改变”得出“rollout policy 大幅改变”。

SWE 两步 checkpoint 中，62,906,299 个保存值变化，BF16 后 123,810 个仍变化，约 99.8032% 的保存值变化被舍入抹除。两次 Adam 与 HF 保存已经完成，但进程随后在最终验证的 vLLM KV cache 唤醒阶段 OOM，exit=1；本次 CPU 审计不代表最后一次验证成功，也不提供训练前后能力提升结论。进程结果见 `runs/rl/swe_separate_2/run-outcome.json`。

抽查的所有 input_layernorm 张量在 BF16 下都与 base 相同。BF16 在较大幅值处间隔较宽，而接近零的投影权重可以用更小间隔表达变化；这会造成不同 tensor 的可见变化比例差异。BF16 将连续的小变化映射为零变化或跨一个量化间隔，因此 BF16 的最大差值也可能大于对应 FP32 差值。

## 结论边界和追加方式

- 抽样只覆盖这些 tensor，不能代表全模型全部参数。
- 这是统一 BF16 cast 的数值审计，不是读取运行中的 vLLM 权重；实际加载、RCCL 同步、个别层 dtype 和 kernel 运算不是本审计的测量对象。
- 保存的小更新可以在后续优化器步骤中累积；当前被舍入不意味着优化无效或永远无法影响推理。
- BF16 值可区分也不保证输出不同，更不保证 reward 或能力提高。行为结论仍看固定验证集。
- 未比较 Miles 的 DCP checkpoint，以保持本次审计有界。

追加新完成的 HF checkpoint 时，使用下面的默认全 run 范围；`--resume` 将复用脚本哈希及源文件 path/size/mtime 未变的记录，仅计算新导出。不要把它当作完整权重文件的密码学校验。

```bash
docker exec ua-lab-cpu /lab/envs/cpu/bin/python   /lab/scripts/cpu-effective-weight-deltas.py --resume
```
